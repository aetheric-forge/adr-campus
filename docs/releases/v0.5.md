# ADR Campus v0.5 — Discover and Understand Decisions

Version 0.5 turns the shared ADR collection into an authorization-aware decision record that members can browse, search, refine, and understand. It delivers the journey defined by [Discover and Understand Decisions](../stories/04-discover-and-understand-decisions.md).

The story document remains authoritative. This release record defines its delivery boundary and links the implementation backlog without restating every acceptance criterion.

## Release Outcomes

At the end of v0.5:

- every active organization member can browse Current, Proposed, Historical, and All shared records without exposing private drafts;
- shared results clearly identify the ADR, lifecycle status, author, attribution, and relevant lifecycle date;
- members can combine lifecycle filters with case-insensitive plain-text search across ADR content, attribution, notes, identifiers, and relevant lifecycle dates;
- members can sort supported columns in either direction with deterministic tie-breaking;
- authorization, matching, sorting, and stable pagination are performed by the server in that order;
- the omnibar provides bounded, delayed suggestions without allowing obsolete responses to replace current results;
- a shared ADR detail page presents its complete content, attribution, decision metadata, and ordered lifecycle history; and
- opening a record and returning to results preserves the member's active view, filters, query, sort, and page.

## Included Story

### Discover and Understand Decisions

The shared decision record begins in the Current view and offers distinct Proposed, Historical, and All-record views. All shared views use one application-owned discovery contract so their authorization, status classification, result presentation, ordering, and empty-state semantics remain consistent.

All-record discovery supports composable lifecycle filters, literal phrase search, sortable columns, and server-side pages of 25 records. Search includes stable identity, proposed content, lifecycle notes, resolved attribution names, and relevant lifecycle dates in stable ISO and displayed human-readable forms. Suggestions use the same authorized scope and matching rules as complete results but return no more than eight likely records.

The detail page shows current persisted state rather than a stale result snapshot. It includes durable lifecycle history and preserves historical attribution when an actor is no longer active. Supersession relationships are displayed and navigable when present; creating those relationships remains part of v0.6.

## Storage and Authority Boundary

- The Library-backed shared-record contract is the only discovery source.
- Workbench drafts, including recoverable or expired drafts, never enter shared queries, counts, suggestions, or direct-record discovery.
- Search, filtering, sorting, and pagination execute on the server over organization-scoped, authorized read models.
- Keycloak remains authoritative for current membership and current display names.
- Stable member identifiers and recorded lifecycle events preserve attribution when current directory information is unavailable.
- Discovery is read-only and cannot change ADR content or lifecycle.

## Deliberately Deferred

Version 0.5 does not include:

- creating or accepting a replacement ADR or otherwise changing supersession relationships;
- saved searches, bookmarks, subscriptions, or notifications;
- fuzzy, stemmed, semantic, wildcard, regular-expression, or operator-based search;
- tags, categories, custom metadata, comments, or discussion;
- exports, printing, public access, analytics, or reporting;
- cross-organization discovery; or
- draft recovery and remaining organization-administration behavior.

## Definition of Done

Version 0.5 is complete when:

1. every applicable acceptance criterion from story 04 passes automated or documented manual QA;
2. all four shared views return exactly their defined lifecycle statuses and never reveal drafts;
3. status filtering, literal phrase matching, column sorting, and page boundaries are composed and evaluated server-side;
4. ordering remains deterministic under tied values and repeated unchanged requests;
5. search validation, delayed suggestions, cancellation, ranking, and the eight-result bound behave as specified;
6. shared details show complete current state, lifecycle history, attribution, and any available relationships;
7. non-members learn no record content, titles, statuses, counts, suggestions, or relationship metadata;
8. result context survives detail navigation and a new signed-in session still begins in Current; and
9. the full solution test suite, solution build, restart verification, and `git diff --check` pass.

The ordered implementation work and QA checkpoints are recorded in the [v0.5 backlog](../backlog/v0.5.md).
