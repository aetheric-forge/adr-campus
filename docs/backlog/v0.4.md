# v0.4 Backlog — Propose, Review, and Decide

This backlog sequences the work required by the [v0.4 release](../releases/v0.4.md). Story acceptance criteria remain authoritative; backlog completion is evidence that the release has implemented them.

## Milestone A — Proposal

### A1. Extend the ADR lifecycle model

- Represent `Proposed`, `Accepted`, and `Rejected` records without allowing arbitrary status assignment.
- Add immutable proposer and proposal-time metadata.
- Add immutable decider, decision-time, outcome, and decision-note metadata.
- Preserve stable ADR identity, organization, author, creation time, and confirmed content through transitions.
- Define transition-specific validation results separately from draft validation.

### A2. Validate proposal content

- Normalize context, decision, and consequences by trimming surrounding whitespace.
- Require 1–4,000 characters and at least one letter or number in every narrative section.
- Reject disallowed control characters while permitting ordinary line breaks.
- Return every incomplete or invalid section in one correctable result.
- Leave the persisted draft unchanged after failed validation.

### A3. Define shared-record persistence

- Add the application-owned repository boundary for proposed and decided ADRs.
- Implement the Library-backed shared-record provider.
- Make Workbench-to-Library proposal atomic from the application's point of view.
- Persist operation IDs and exact confirmed versions for idempotent retries.
- Preserve durable lifecycle metadata suitable for later Archive projections.

### A4. Implement the proposal command

- Require current active membership and current authorship at commit time.
- Require the ADR to remain a non-expired `Draft` at the exact previewed version.
- Move the existing stable ADR to `Proposed` without creating a second identity.
- Remove it from ordinary private-draft editing and listing after success.
- Return the persisted result for genuine retries and the current state for conflicts.

### A5. Implement proposal browser flow

- Identify incomplete and invalid sections from the draft page.
- Present a confirmation preview tied to the current draft version.
- Explain that confirmation makes content organization-visible and read-only.
- Preserve `Draft` state when the author cancels or leaves.
- Show the persisted Proposed record after successful confirmation.
- Refuse edit routes for proposed content.

### QA Checkpoint A — Proposal

- Complete, incomplete, invalid, normalized, stale-preview, unauthorized, and retry scenarios pass.
- Another active member can read the proposal but cannot edit or decide it unless they are a maintainer.
- A non-member learns no proposal content.
- Restarting the application preserves the proposal and its metadata.
- No successful or failed operation leaves both an editable draft and a contradictory proposal.

## Milestone B — Review and Decision

### B1. Validate decision notes

- Permit an empty acceptance note.
- Require a non-empty rejection reason.
- Normalize surrounding whitespace.
- Enforce the 1,000-character maximum, letter-or-number requirement, and control-character rules.
- Preserve the proposal after invalid or cancelled decisions.

### B2. Implement decision commands

- Recheck active Maintainer authority at confirmation time.
- Tie confirmation to the exact persisted proposal reviewed.
- Permit documented self-approval.
- Atomically record `Accepted` or `Rejected`, one decider, one decision time, and the normalized note.
- Make the first persisted decision final.
- Make retries idempotent and concurrent opposing decisions deterministic.

### B3. Implement shared proposal views

- Replace the Proposed placeholder with the minimal organization-visible proposal list.
- Show status, title, author, proposer, and proposal time.
- Display the immutable proposal content on its review page.
- Show decision controls only to active maintainers.
- Keep the member read experience distinct from maintainer actions.

### B4. Implement accept/reject confirmation

- Offer acceptance with an optional note.
- Offer rejection with a required reason.
- Preview the selected final outcome and note before committing.
- Preserve entered notes after validation or persistence failures.
- Show the persisted outcome, decider, decision time, and note after success.

### B5. Add minimal decided-record placement

- Include Accepted ADRs in the Current view.
- Include Rejected ADRs in the Historical view.
- Keep Accepted and Rejected records readable by active members.
- Never represent Rejected or Proposed ADRs as current architecture.
- Defer general discovery controls to v0.5.

### QA Checkpoint B — Decision

- Acceptance with no note and with a valid note passes.
- Rejection requires and preserves a valid reason.
- Ordinary members cannot decide proposals.
- Authority removed after opening the page is rechecked and denied at confirmation.
- Two concurrent maintainers produce exactly one final outcome.
- A retried operation preserves the original decider, time, note, and outcome.
- Accepted and Rejected records survive restart and remain immutable.

## Release QA

- Run all automated domain, application, provider, authorization, and browser tests.
- Manually carry one ADR through `Draft → Proposed → Accepted`.
- Manually carry another ADR through `Draft → Proposed → Rejected`.
- Confirm proposal cancellation and decision cancellation create no lifecycle change.
- Confirm role labels, status badges, and navigation never imply false authority.
- Confirm no private draft metadata appears in shared views.
- Confirm Redis-backed Workbench and Library state survive application restart.
- Confirm `git diff --check` and the complete solution build pass.
