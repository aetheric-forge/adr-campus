# v0.6 Backlog — Supersede a Decision

This backlog sequences the work required by the [v0.6 release](../releases/v0.6.md). The [supersession story](../stories/05-supersede-a-decision.md) remains authoritative; backlog completion is evidence that the release has implemented it.

**Status:** Complete — Milestones A through D and release QA were delivered in v0.6.

## Milestone A — Intended Supersession in Drafts

### A1. Model the intended target

- Add an optional intended supersession target to a private ADR draft.
- Preserve the replacement's independent stable identity, organization, author, content, timestamps, and version.
- Allow at most one target and distinguish intended supersession from a completed relationship.
- Keep ordinary drafts valid when no intended target is present.
- Persist intended-target changes through the existing Workbench provider contract.

### A2. Validate target selection

- Require the selected target to belong to the same organization and currently have `Accepted` status.
- Refuse self-reference and relationships that would create a cycle.
- Reveal no cross-organization target content or metadata through validation outcomes.
- Preserve the last valid saved target when a requested change is invalid.
- Reuse application-owned validation outcomes across commands and browser presentation.

### A3. Begin and edit replacement drafts

- Add an authorized command that creates a new private draft from an accepted ADR and records the initiating member as author.
- Make retry behavior create exactly one replacement draft for one client-generated operation identifier.
- Let only the active author change or remove the intended target while the ADR remains a draft.
- Recheck active membership, authorship, target state, and draft version when changes are persisted.
- Leave every possible target unchanged when a replacement draft is created or edited.

### A4. Implement the replacement drafting experience

- Offer **Propose a replacement** only from an accepted ADR detail view.
- Show the intended target on draft, edit, and preview pages without exposing it to other members while the draft is private.
- Let the author select another eligible accepted ADR or remove the target.
- Explain invalid or stale selections without discarding valid draft content.
- Preserve optimistic-concurrency behavior for content and target edits.

### QA Checkpoint A — Replacement Draft

- Creating a replacement produces one new private ADR with its own identity and leaves the target accepted and unchanged.
- Ordinary draft creation remains unchanged and produces no intended relationship.
- Changing and removing a target work only for the active author of a draft.
- Non-accepted, cross-organization, self-referential, cyclic, stale, unauthorized, and concurrent edits preserve the last valid state.
- Replacement draft content and target remain absent from every shared discovery surface.
- Workbench persistence and application restart preserve the intended target.

## Milestone B — Freeze and Share the Intended Target

### B1. Extend proposed-record metadata

- Add immutable intended-target metadata to a proposal without treating it as completed supersession.
- Preserve an absent target for ordinary proposals.
- Carry the exact target from the confirmed draft version into the proposed record.
- Make intended-target metadata durable and suitable for lifecycle history.

### B2. Revalidate proposal

- Recheck that the intended target belongs to the organization and remains `Accepted` when proposal commits.
- Keep the replacement in `Draft` if its target is stale or otherwise invalid.
- Require the author to remove or replace a stale target before retrying proposal.
- Preserve existing proposal atomicity, idempotency, and exact-version confirmation.

### B3. Present proposed replacements

- Identify a proposed replacement and its intended target in discovery and detail read models.
- Link authorized members from the proposal to the currently persisted target.
- Show the intended target on maintainer review and decision confirmation surfaces.
- State clearly that the target remains accepted and in effect until the replacement is accepted.
- Degrade safely when an authorized linked record is unavailable.

### QA Checkpoint B — Proposed Replacement

- Proposal freezes the exact intended target from the confirmed draft revision.
- Proposal against a target that changed state fails without moving or duplicating either ADR.
- Proposed replacement details expose the intended relationship to active members but create no reciprocal completed relationship.
- The target remains in Current and the replacement remains in Proposed.
- Ordinary proposals continue to work without target metadata.
- Non-members learn no proposal, target, count, or relationship metadata.

## Milestone C — Atomic Supersession Decision

### C1. Model completed supersession

- Represent the accepted replacement's direct `supersedes` relationship and the target's reciprocal `superseded by` relationship.
- Record one supersession time equal to the replacement's decision time.
- Preserve the target's original content, identity, author, proposal metadata, acceptance metadata, and earlier history.
- Preserve the replacement's independent content and lifecycle metadata.
- Retain only direct links when a superseded replacement later becomes a target itself.

### C2. Implement acceptance as one operation

- Recheck active Maintainer authority and the exact proposed replacement at commit time.
- Recheck that the immutable intended target remains in the same organization and `Accepted`.
- Atomically change the replacement to `Accepted`, the target to `Superseded`, and persist reciprocal relationships and lifecycle events.
- Refuse self-referential, cross-organization, cyclic, stale-target, or partially persistable transitions.
- Return no success and expose no intermediate state unless the whole operation commits.

### C3. Preserve rejection behavior

- Reject a proposed replacement under the ordinary review-and-decide rules.
- Retain its immutable intended-target history.
- Leave the target accepted and unchanged.
- Create no completed or reciprocal supersession relationship.

### C4. Make acceptance retry- and concurrency-safe

- Persist the operation identifier with the complete supersession outcome.
- Return the original statuses, decider, decision time, note, relationships, and supersession time for a genuine retry.
- Prevent duplicate decision events, lifecycle events, and relationship records.
- Allow only the first competing replacement to be accepted against a target.
- Leave losing replacement proposals `Proposed` so a maintainer may reject them with a reason.

### QA Checkpoint C — Supersession Commit

- Successful acceptance changes exactly two ADR statuses and creates exactly two reciprocal direct links with one timestamp.
- Rejection creates no completed relationship and leaves the target current.
- Stale-target acceptance preserves both records and records no decision.
- Concurrent replacements produce one accepted replacement, one superseded target, and no silently rejected or retargeted proposals.
- Repeated operation identifiers return the original result without duplicate history.
- Injected persistence failures never expose a partial transition or one-sided relationship.

## Milestone D — Discovery, Detail, and History

### D1. Project supersession lifecycle history

- Add completed supersession events to the ordered lifecycle read model.
- Preserve stable actor identifiers, effective attribution, direct relationship identifiers, and the shared supersession time.
- Keep intended-target history on rejected replacements without claiming a completed relationship.
- Keep history derivable from authoritative persisted state and events.

### D2. Update discovery semantics

- Treat `Superseded` as historical and never as current architecture.
- Place the accepted replacement in Current and the superseded target in Historical immediately after commit.
- Include superseded records correctly in All, status filters, search, sorting, pagination, and counts.
- Preserve deterministic ordering and existing result-context behavior.
- Ensure no partial or cached projection contradicts the committed lifecycle.

### D3. Make relationships navigable

- Show an accepted replacement's direct predecessor and a superseded ADR's direct successor.
- Preserve both directions when a replacement later becomes superseded itself.
- Navigate each link to current persisted detail while retaining a route back to discovery results.
- Explain an unavailable linked record without revealing unauthorized metadata.
- Avoid flattening chains or implying indirect supersession.

### QA Checkpoint D — Understand Supersession

- Current, Historical, All, filtered, searched, sorted, and paginated views classify both records correctly.
- Detail and lifecycle history preserve all earlier content, attribution, decisions, and direct links.
- An A-to-B-to-C chain remains A-to-B and B-to-C and is navigable in either direction.
- Rejected replacement details show intended history while their targets show no completed relationship.
- Non-members and cross-organization requests reveal no relationship metadata.
- Discovery context survives navigating through supersession links and back to results.
