# v0.5 Backlog — Discover and Understand Decisions

This backlog sequences the work required by the [v0.5 release](../releases/v0.5.md). The [discovery story](../stories/04-discover-and-understand-decisions.md) remains authoritative; backlog completion is evidence that the release has implemented it.

## Milestone A — Shared Browse Model

### A1. Define discovery criteria and results

- Define Current, Proposed, Historical, and All shared-record views as application-owned criteria.
- Represent `Proposed`, `Accepted`, `Rejected`, and future `Superseded` status selections without accepting arbitrary values.
- Define a shared result containing stable ADR identity, title, status, author, relevant attribution, and relevant lifecycle date.
- Define explicit empty, unavailable, unauthorized, invalid-request, and successful query outcomes.
- Keep discovery contracts independent of Razor components and persistence providers.

### A2. Implement the authorization-aware shared query

- Require current active membership before querying or returning counts.
- Scope every query to exactly one organization.
- Read only shared Library records and exclude every Workbench draft by construction.
- Classify Current, Proposed, Historical, and All results from persisted lifecycle state.
- Order default browse results by relevant lifecycle event descending and stable ADR identity as the final tie-breaker.

### A3. Consolidate shared browse pages

- Replace the separate minimal v0.4 list logic with the shared discovery query.
- Present stable identifier, title, text status, author display name, relevant lifecycle date, and applicable proposer or decider.
- Distinguish an empty organization from a view that has no matching shared records.
- Preserve the existing proposal decision controls without mixing commands into the discovery query.
- Make the Current view the default for a new signed-in session.

### QA Checkpoint A — Browse

- Each view returns exactly its defined statuses in deterministic order.
- Current never contains Proposed, Rejected, or Superseded records.
- Historical never represents a rejected record as current architecture.
- Active members see organization-scoped shared results; non-members receive no results or counts.
- Private, incomplete, expired, and recovery-window drafts are absent from every browse surface.
- Empty-organization and empty-view messages are accurate and distinct.

## Milestone B — Filtering, Sorting, and Pagination

### B1. Add composable status filtering

- Permit any combination of shared lifecycle statuses in All shared records.
- Treat no selected status as all shared statuses.
- Reject or ignore undefined status values without broadening the query.
- Display every active filter and provide a clear way to reset them.
- Reset to page one when the view or filters change.

### B2. Add deterministic server-side sorting

- Support stable identifier, title, status, author, and relevant lifecycle date columns.
- Make a selected column the primary sort and selecting it again reverse direction.
- Apply stable ADR identity as the final tie-breaker for every sort.
- Resolve author display names consistently for sorting and presentation.
- Expose the active column and direction accessibly in the browser.

### B3. Add stable server-side pagination

- Apply authorization, filters, sorting, and pagination in that order.
- Return no more than 25 results per page without loading the complete result set into the browser.
- Return current page, earlier/later availability, and enough state to build stable navigation.
- Preserve view, filters, sort, and page when moving between pages.
- Handle invalid, empty, and out-of-range pages without revealing excluded record counts.

### QA Checkpoint B — Refine Results

- Status filters compose correctly and an empty selection means all shared statuses.
- Every sortable column works in both directions over the complete matching set.
- Tied values produce stable repeatable order using ADR identity.
- More than 25 results paginate without duplicates or omissions.
- Changing view, filters, or sort returns to page one; page navigation preserves all other criteria.
- Non-member and cross-organization requests cannot infer totals or page availability.

## Milestone C — Search and Omnibar

### C1. Validate and normalize search phrases

- Trim surrounding whitespace and treat an empty phrase as clearing search.
- Require 3–200 characters and at least one letter or number for non-empty searches.
- Reject control characters while treating punctuation and operator-like text literally.
- Return a correctable validation result without executing an invalid query.

### C2. Implement complete shared-record search

- Match case-insensitively across stable identity, title, context, decision, consequences, attribution display names, decision notes, and relevant lifecycle date.
- Match lifecycle dates literally in ISO, displayed abbreviated-month, and displayed full-month forms without interpreting date expressions or ranges.
- Apply search only inside the selected view and status filters.
- Rank unsorted results by exact stable-identifier match, then title match, then other-content match.
- Within equal rank, order by relevant lifecycle event descending and stable identity.
- Preserve a member-selected column sort instead of applying relevance ranking.
- Distinguish no search matches from an empty organization or empty filtered view.

### C3. Implement bounded omnibar suggestions

- Wait approximately 300 milliseconds after at least three valid normalized characters.
- Cancel outstanding requests or ignore responses for obsolete input.
- Use the same authorization, view, status-filter, matching, and ranking rules as complete search.
- Return and display no more than eight suggestions.
- Rank exact identifiers before titles and other content.
- Offer **View all results** when additional matches exist.
- Open a selected suggestion directly and submit the phrase into complete results.

### QA Checkpoint C — Search

- Search matches every specified field case-insensitively and excludes out-of-scope statuses.
- Date search matches ISO and displayed human-readable lifecycle dates, including useful partial phrases such as a year.
- Operator, wildcard, and regular-expression characters are handled only as literal text.
- Invalid phrases produce validation guidance and execute no query.
- Empty search preserves view and filters while clearing text matching.
- Suggestions do not start too early, never exceed eight, and stale responses never replace current input.
- Suggestions, complete-result counts, and ranking reveal nothing to non-members.

## Milestone D — Detail, History, and Navigation Context

### D1. Build durable lifecycle history

- Project proposal and decision events into an ordered application read model.
- Preserve stable actor identifiers, effective attribution, event type, and event time.
- Include audited pre-proposal author reassignment when such history exists.
- Represent supersession relationships and events when introduced without inventing them for existing records.
- Keep history derivable from authoritative persisted lifecycle data.

### D2. Complete the shared ADR detail page

- Display stable identity, title, exact proposed content, and unambiguous current lifecycle meaning.
- Display author and creation time, proposer and proposal time, and applicable decision metadata.
- Display ordered lifecycle history without exposing private draft revisions or metadata.
- Resolve current display names retroactively when available and identify former actors when they are not.
- Show and navigate supersession relationships when present, with an unavailable-linked-record explanation.

### D3. Preserve result context

- Carry view, status filters, query, sort, page, and stable result ordering into detail navigation.
- Return to the prior result context when underlying records have not changed.
- Show current persisted detail when a record changed after the result page was produced.
- Preserve a route back to the earlier results even when the record no longer matches them.
- Do not restore discovery state from an earlier signed-in session; begin a new session in Current.

### QA Checkpoint D — Understand and Return

- Proposed, Accepted, and Rejected details show complete current lifecycle content and history.
- Historical actors remain intelligible when they leave or their current display name changes.
- No detail or history view exposes private draft contents, revisions, recovery state, or metadata.
- Result context round-trips through detail for browse, filtered, sorted, searched, and paginated results.
- A record changed after listing displays its current status without corrupting the return context.
- Conditional supersession links are correct when relationship data exists and degrade clearly when unavailable.

## Release QA

- Run all automated domain, application, provider, authorization, and browser tests.
- Seed more than 25 mixed-status shared ADRs with tied sort values and varied attribution.
- Manually exercise all four views, combined filters, every sortable column, and forward/back pagination.
- Search every supported field and verify literal punctuation, invalid phrases, suggestion delay, cancellation, and bounds.
- Open records from multiple result contexts and confirm exact restoration on return.
- Confirm direct access, browse, counts, pagination, search, and suggestions all fail closed for a non-member.
- Confirm no private draft or draft metadata appears anywhere in shared discovery.
- Restart the application and confirm shared results, lifecycle history, and deterministic ordering remain intact.
- Confirm `git diff --check` and the complete solution build pass.
